# Lab 12 redesign: self-contained exploitation target

Goal: run Lab 12 (Vulnerability exploitation) **without the Metasploitable 2 download**. The
"provided production system" the student audits becomes a container stack built into the Kali
VM. Scenario source: `lab-instructions/2026-2027/proposals/Cyber_PL_Lab_Eksploitacja_14.08.docx`
(workspace). Student instructions live in the workspace; this file is the build/architecture side.

## Decisions
- **Target delivery:** Docker on Kali. The target runs as container(s) on a Docker bridge with a
  fixed IP; the student recons and attacks that IP from Kali. One VM, nothing downloaded at lab
  time (images built into the OVA, like Juice Shop).
- **Architecture scope:** amd64 first. arm64 once the JDK 8 / vsftpd base images are confirmed to
  build on ARM (see Open items). The role is a no-op on arm64 until then.
- **Instruction depth:** the lab text gives the narrative, task groups, the three documented
  attack vectors as objectives, and tool pointers. Exploit payloads/commands are authored and
  tested by the instructor on the running VM, not shipped in this repo.

## Topology
```
Kali Lab 2026-2027 (attacker + Docker host)
  eth0  172.16.96.0/24  Lab NAT Network (unchanged; labs 8-11)
  docker bridge  cyberlab-lab12  10.12.0.0/24
     └── target  10.12.0.10   the "provided system"
```
The student works from Kali against `10.12.0.10`. The Log4Shell callback (JNDI/LDAP + class
serving) goes target → Kali's bridge gateway (10.12.0.1), which is reachable from the container.

## The target image
One designed vulnerable image (not a stock app container), based on an older Debian/JDK 8 base so
the old software compiles. It carries three weaknesses so task 2.3 ("document 3 attack scenarios")
has real material, and a seeded post-exploitation chain for task group 3.

Two independent exercises on one target:
- **A — standalone.** vsftpd 2.3.4 backdoor: recon finds the service, identify the CVE, exploit the
  backdoor. Self-contained; not part of the chain, so its shell privilege doesn't matter and vsftpd
  runs as root (its libcap startup won't run non-root anyway).
- **B → C — the chain.** Log4Shell gives an unprivileged foothold (`app`), which leads to a
  credential and a writable root cron job (privesc), then SSH + reverse-shell persistence.

| Vector | Service / mechanism | CVE / class | Role in the scenario |
|---|---|---|---|
| A | vsftpd 2.3.4 (compiled from nikdubois/vsftpd-2.3.4-infected, port 21, `local_enable=YES` so the `:)` backdoor is reachable) | CVE-2011-2523 backdoor | **standalone**: version → CVE → backdoor RCE |
| B | Log4Shell "salary" Spring app (JDK 8, Log4J 2.14.1, port 9876) | CVE-2021-44228 | chain start: unprivileged foothold as `app` (task 3.1) |
| C | writable root cron job | privesc + persistence | `app` → root, then sshd + user + reverse shell (tasks 3.4-3.6) |

**Container safety:** the container runs **unprivileged, no `--privileged`, no Docker socket
mounted**, so "root" is the target's own root and a student cannot escape to the Kali host. The
chain's foothold (`app`, the Log4Shell service user) is non-root; vector C elevates it to
container-root. vsftpd (A) runs as root but is a separate exercise.

**Vector C mechanism — writable root cron job.** A root crontab entry runs a helper script (e.g.
`/opt/report/run.sh`) every minute. The script is owned by root but **group-writable** by a group
the foothold account belongs to (a realistic perms misconfig), so the student overwrites it and the
next tick executes their code as root. This makes the target **multi-process**: a lightweight
supervisor (supervisord) runs cron + vsftpd + the Java app. sshd is installed but **not started** —
the student enables it as part of task 3.5. Cron cadence is 1 minute (students wait ≤60 s).

Post-exploitation chain (task group 3), seeded into the image:
1. Log4Shell (B) lands as the unprivileged `app` account (task 3.1-3.2).
2. A config file readable by that account holds a credential (task 3.3).
3. **Vector C**: the credential + the privesc mechanism reach container-root (task 3.4).
4. From root: install/enable sshd, add an account (task 3.5), reverse shell out (task 3.6).

Notes: the seeded credential is **generated by `entrypoint.sh` on every container start**, never
baked into the image. It must not be a constant in this repo (the repo is public), and a build-time
`--build-arg` is no good either: it is recorded in `docker history`, and `stud` is in the docker
group on the student VM, so the value could be read off the image without touching the chain.
Generating it per start also gives every `lab12-target reset` a fresh value, so it cannot be passed
between students. Finding it on the box is the exercise; the value need not be secret in advance.
The Log4Shell CTF flag is removed/repurposed (the lab measures RCE + escalation, not a fixed flag).

## Kali attacker side (added to the build)
- Docker engine (`docker.io`), the prebuilt target image, and the build context under
  `/usr/local/share/cyberlab/lab12/`, with a `lab12-target` helper to start/stop/reset the
  container. Plain `docker run`, **not compose**: Kali has no compose v2 package, and a single
  container does not need one.
- **No attacker tooling for vectors B/C is installed.** Standing up the JNDI/LDAP referral and
  class-serving side (e.g. marshalsec) is part of the student's work, so it is deliberately kept
  out of the OVA. Metasploit, nmap, searchsploit, netcat and socat already come from the `tools`
  role and cover vector A and the recon tasks.

## Task-group mapping (proposal → services)
- **1. Recon / fingerprinting** (nmap TCP+UDP, versions, OS, banners, WhatWeb/NSE) → scan
  `10.12.0.10`; vsftpd 21 and the web app on 9876 reveal versions.
- **2. Service audit + CVE** (searchsploit, NVD, Nikto/NSE) → map vsftpd 2.3.4 and Log4J 2.14.1 to
  CVEs; **document 3 attack vectors** (A, B, C).
- **3. Exploitation** → RCE PoC (3.1) via one vector; shell (3.2); creds in config (3.3);
  privileged component (3.4); sshd + new user (3.5); reverse shell (3.6). Instructor authors these.
- **4. Report** → PTES/OWASP-style writeup, evidence, CVSS, remediation.

## Build & test on the VM
The role runs as part of `kali.yml`, or the target can be built and checked on its own. On the Kali
build VM (or a clone), with the repo copied in and Docker available:
```bash
# 1. build the image (or let `ansible-playbook kali.yml` do it)
docker build -t cyberlab/lab12-target:2026 roles/lab12_target/files/target
# 2. install the helper (or apply the role)
sudo install -m755 roles/lab12_target/files/kali/lab12-target /usr/local/bin/lab12-target
sudo install -d /usr/local/share/cyberlab/lab12 && sudo cp -r roles/lab12_target/files/target/. /usr/local/share/cyberlab/lab12/
# 3. verify the environment supports A/B/C (does NOT run exploits)
bash roles/lab12_target/tests/verify.sh
```
`verify.sh` runs 11 checks: the vsftpd 2.3.4 banner on :21 and the binary in place (vsftpd runs as
**root by design** — vector A is standalone), the salary app on :9876 with JNDI lookups enabled and
running non-root, the writable root cron reachable from the foothold account, the seeded credential,
and that sshd is installed but not started. Note it **starts the container**, so it is not a
read-only check. It runs no exploits; the chain itself is authored and tested by the instructor on
top of this.

Testing note: the sealed snapshot has SSH/host keys removed, so build/test starts from a login the
instructor performs (clone `kali-2026.2-build`, boot, then run the commands above).

## Seal & distribution
The target is built into the Kali OVA (no download for students), so the normal
build → seal → export flow ([maintainer.md](maintainer.md)) applies, plus:
- The image is built by the `lab12_target` role during `ansible-playbook kali.yml`
  (amd64). Nothing special at seal time except cleanup.
- `build/seal.yml` prunes Docker before the zero-fill: it removes the build cache
  and every image not in the `cyberlab/` repo (the base + build-stage images the
  final image does not need), keeping `cyberlab/lab12-target:2026`. Without this
  the OVA carries ~1.5 GB of maven/debian/temurin layers and cache.
- `docker.io` is `state: present` (kept by apt autoremove) and enabled, and
  `stud` is in the docker group, so on a sealed OVA `lab12-target start` works on
  first boot with no rebuild.
- Distribute from a full `kali.yml` build on the real build VM — not an ad-hoc
  clone with only Docker + the image hand-installed.

Post-seal check (on a booted clone of the sealed VM): `lab12-target start`, then
`bash roles/lab12_target/tests/verify.sh` should pass 11/11, and the docker
images list should show only `cyberlab/lab12-target:2026`.
